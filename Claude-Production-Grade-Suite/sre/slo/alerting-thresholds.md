# Minimal Initial Alerting Set — estoque-saas (single VPS, Docker Compose)

**Authority:** SRE defines WHAT should alert and AT WHAT THRESHOLD. DevOps picks and wires the actual monitoring stack (Prometheus+Alertmanager, Uptime Kuma, Grafana Cloud free tier, Better Stack, a cron+curl script — whatever fits a single-VPS Docker Compose budget) in SHIP. Nothing below is tool-specific by design.

**Philosophy for this stage:** every alert must map to something a 1-2 person team can actually act on at 2am, or it shouldn't page. Favor a short list of high-signal alerts over comprehensive coverage. Tie every alert to either an SLO above or to a failure mode that has no other detection (infra-level signals Prometheus-style SLI math won't catch, like disk filling up).

Containers referenced (from `docker-compose.yml`): `app` (web), `worker`, `postgres`, `redis`.

## Alert set

| # | Alert | Signal | Threshold | Severity | Why | Runbook |
|---|---|---|---|---|---|---|
| 1 | **App container unhealthy** | `app` container health check (`GET /api/healthz`, already defined in compose) failing | Failing for > 2 consecutive checks (≈20-30s at current 10s interval) OR container in restart loop (> 3 restarts / 10 min) | Critical / page | The whole product is down for every tenant. | *(general outage — not scoped here; standard "app is down" triage)* |
| 2 | **Worker container down or not consuming jobs** | `worker` container not running, OR container running but BullMQ "active" job count stays at 0 while "waiting" count is > 0 for a sustained period | Container down > 1 min → page. "Waiting > 0 and active == 0" for > 5 min → page. | Critical / page | Worker has **no health check today** (gap — see finding below); a "container running" check alone gives false confidence — it can be up but wedged (e.g. crashed job loop, Redis connection lost silently). | `docs/runbooks/worker-queue-backlog-growing.md` |
| 3 | **Postgres connection pool near exhaustion** | Active connections as % of `max_connections` | Warn at 80% for > 5 min. Critical/page at 95% for > 2 min. | Warning → Critical | Single Postgres instance (ADR-001/002); exhaustion blocks every tenant's requests simultaneously — direct hit to `web-core-availability-slo`. Ranked the #1 capacity bottleneck at 1x scale — see `Claude-Production-Grade-Suite/sre/capacity/bottleneck-analysis.md` §1. | `docs/runbooks/postgres-connection-pool-exhaustion.md` (added T9b/SHIP) |
| 4 | **Worker queue backlog growing unboundedly** | BullMQ "waiting" job count per queue (`nfe-import`, `billing`, `alerts`) | `alerts` queue: warn if waiting > 20 for > 2 min (this queue has a 60s SLA — even a small backlog is meaningful). `nfe-import`/`billing` queues: warn if waiting count is both > 50 AND has grown (not shrunk) over the last 10 min (i.e. genuinely backing up, not just a burst). Critical/page if any queue's waiting count exceeds 500 or keeps growing for > 30 min. | Warning → Critical | Distinguishes "busy" from "stuck" — the growth trend matters more than a static count for a low-volume MVP. Directly protects `job-alert-scan-slo`, `job-nfe-import-slo`, `job-billing-charge-generation-slo`. | `docs/runbooks/worker-queue-backlog-growing.md` |
| 5 | **Disk usage on the Postgres volume** | Disk % used on the volume backing `postgres_data` (and, per T9b review, `uploads_data` too — see `Claude-Production-Grade-Suite/sre/capacity/bottleneck-analysis.md` §3, unbounded aggregate growth with no retention policy today) | Warn at 80%. Critical/page at 90%. | Warning → Critical | A single VPS with a single disk — Postgres refusing writes because the disk is full is a full outage with a slow, preventable buildup. Cheapest alert to set up, highest regret if skipped. This is not hypothetical for this project — this exact incident type was hit once already during this project's own development session. | `docs/runbooks/disk-full-vps.md` (added T9b/SHIP) |
| 6 | **PagBank webhook error rate / endpoint down** | 5xx rate (or non-2xx ack rate) on the webhook receiver route, over a short window | Warn if non-2xx rate > 5% over 15 min. Critical/page if non-2xx rate > 20% over 5 min, OR zero webhook deliveries received for > 6h while charges are known to be scheduled (silence can mean "gateway can't reach us," not "nothing happened"). | Warning → Critical | Billing-critical (BRD Epic 9) — directly protects `pagbank-webhook-availability-slo` / `pagbank-webhook-ack-slo`. | `docs/runbooks/pagbank-webhook-processing-stopped.md` |
| 7 | **PagBank webhook reconciliation stuck** | Time since a received (ack'd) webhook event was fully reconciled (subscription/invoice state updated) | Warn if any event is un-reconciled for > 5 min. Critical/page if > 15 min (matches `pagbank-webhook-reconciliation-latency` hard_ceiling). | Warning → Critical | This is the failure mode where the webhook was received fine but the *processing* of it silently stalled (e.g. worker down, queue stuck) — ack success alone (#6) won't catch it. | `docs/runbooks/pagbank-webhook-processing-stopped.md` |
| 8 | **Redis memory pressure / unavailability** | Redis `used_memory` as % of configured `maxmemory` (or of instance RAM if unbounded); also covers Redis being fully down, not just under memory pressure | Warn at 80%. Critical/page at 95%. Redis down (failed `PING`) is always Critical, no threshold. | Warning → Critical | Redis serves THREE independent concerns in this system — BullMQ queue, rate-limit store (H-5), session/query cache (C4 diagram) — memory pressure or an outage risks evicting queued jobs (possible data loss, no persistence flags confirmed configured — see runbook), not just cache misses or unprotected login. On a single VPS there's no Redis failover to fall back on. | `docs/runbooks/redis-unavailable.md` (added T9b/SHIP) |
| 9 | **Possible cross-tenant data leak (RLS)** | Any occurrence of a query result crossing tenant boundaries — detected via the automated schema-scan test QA runs (ADR-002: "teste automatizado que varre o schema e falha o build se alguma tabela com tenant_id não tiver RLS habilitada") failing in CI, OR an application-level assertion/canary that periodically verifies RLS is enforced for a known test tenant pair in production | Any single occurrence | **Critical / page immediately** — no threshold, no averaging window. | This is a security incident, not a reliability statistic — see runbook. Zero tolerance by design; do not "wait for a trend." | `docs/runbooks/postgres-rls-misconfiguration-cross-tenant-leak.md` |
| 10 | **TLS certificate nearing expiry** | Days until reverse-proxy TLS cert expiry (out of scope of app architecture per C4 notes, but still a single-VPS operational risk since there's no CDN/LB automating renewal for you) | Warn at 14 days remaining. Critical/page at 3 days. | Warning → Critical | Silent expiry on a single VPS with no failover = full outage with zero warning otherwise. Cheap insurance. | **T9b/SHIP update:** DevOps implemented Caddy (`docker-compose.prod.yml`) with automatic Let's Encrypt renewal (`production-deployment.md` §1) — not certbot, superseding this row's original "e.g. certbot" note. Caddy's automation lowers the *likelihood* of this firing but does not eliminate the failure mode (DNS/domain misconfiguration, ACME rate-limiting, Caddy itself down) — keep this alert active, it's still cheap insurance against a silent renewal failure. *(no dedicated runbook — low enough likelihood/frequency at this stage that a dedicated runbook is not prioritized this pass; general "check Caddy logs for ACME errors, confirm DNS still points at this VPS" triage is sufficient until this fires for real)* |
| 11 | **Stock write latency spike (advisory-lock contention)** | `web-write-latency-slo` breach isolated to stock-mutating endpoints specifically (entries/exits/sales/transfers/NF-e confirm), OR direct signal via `pg_stat_activity` rows with `wait_event_type = 'Lock'` and `query LIKE '%pg_advisory_xact_lock%'` | Warn if any such wait exceeds 2s for > 5 min. Critical/page if any single wait exceeds 10s, or if requests on these endpoints start timing out rather than just slowing. | Warning → Critical | **New in T9b/SHIP** — code-reviewer finding CR-1 (`services/app/src/modules/stock/balance.ts:16`) introduced `pg_advisory_xact_lock` to fix a lost-update/oversell bug; the lock is correct and should not be rolled back, but it is a new contention point with no `lock_timeout` configured today (`production-readiness/readiness-review-ship.md` §3/§4), so a hot-SKU burst can currently degrade into unbounded waiting rather than bounded queueing. See `capacity/hi2-cr1-slo-impact-review.md` for the full analysis. | `docs/runbooks/stock-write-lock-contention.md` (added T9b/SHIP) |

## Explicitly NOT alerting on (at this stage)

To keep the list actionable for a 1-2 person team, the following are deliberately **not** initial alerts — track them in dashboards/logs instead, revisit if they become real problems:

- CPU utilization alone (without a corresponding latency/availability SLO breach) — noisy, rarely actionable on a single small VPS without more context.
- Individual slow-query alerts (covered in aggregate by the latency SLOs above; a query-level alert is premature before there's a query-performance dashboard to triage against).
- `web-dashboard-availability-slo` burn — tracked, never pages (see error-budget-policy.md §2).

## Finding for DevOps (infra gap, not an SRE artifact to fix directly)

The `worker` service in `docker-compose.yml` has **no `healthcheck` block today** (unlike `app`, `postgres`, `redis`). Docker Compose/`depends_on: condition: service_healthy` for `worker` isn't possible without one, and alert #2 above needs *some* liveness signal beyond "process exists." Recommend DevOps add a lightweight healthcheck (e.g. a small HTTP/TCP liveness port the worker process opens, or a "last heartbeat" timestamp file/Redis key the worker touches on each poll loop) before wiring alert #2 for real. This is an infra implementation detail (DevOps owns `docker-compose.yml`) — SRE is flagging the requirement, not prescribing the mechanism.
